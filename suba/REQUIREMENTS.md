# suba 需求基线

日期：2026-10-14，范围修订 0.2。状态：K0 已验收；根据用户确认将首版原生构建与内核部署分开，修订依据见 [SCOPE_REVISION](design/SCOPE_REVISION.md)。本文是交付要求，不是完整系统实现完成声明。

## 1. 目标与优先级

suba 是 konOSuba 的新内核与系统环境，目录为 `suba/`。`SOS/` 已弃用，不继承其技术路线、需求草案或预算。

项目优先级为 **自举、简单、现代**，重要性依次降低。学习者应能沿同一个系统追踪源码编辑、编译、装载、执行、资源使用、进程协作、结束与回收的完整过程，并由此理解现代系统软件。

借鉴 Oberon 的整体设计方法：各组成部分围绕同一套系统约定设计并构建，局部样本使用实际系统机制。模块示例和算法演示不能代替集成系统的行为验收。

整体设计不等于预先实现所有扩展。实施可以分阶段，但每个阶段必须服务于已明确的完整系统，不能让互不相连的试验逐渐替代整体架构。

## 2. 实现与平台

- 主要使用当前 S-next 实现。
- 启动、陷入和必要机器操作使用少量汇编；汇编的作用、接口和成本必须明确。
- 正式运行平台为 QEMU RISC-V 64，首个完整版本采用单核、多进程。
- 固定一组 QEMU 自带虚拟设备，提供图形输出、键盘、鼠标和块存储。具体设备型号、内存配置及启动参数由架构方案选择并验证。
- 使用本系统自己的运行和服务接口，暂不兼容 Linux；不要求 POSIX 或完整 libc。
- 网络、声音、USB、实体板卡适配及多核不纳入当前交付范围。

“QEMU 虚拟设备”限定平台来源，不表示无需显式配置就具有全部图形和输入设备。运行脚本必须固定正式机器配置，使验收可重复。

## 3. 系统内开发与自举

完整系统必须允许在 suba 内：

1. 阅读、编辑和保存 S-next 源码及必要的汇编源码。
2. 运行 S-next 编译器，构建普通应用并执行产物。
3. 编辑并重新构建 S-next 编译器自身，验证原生固定点及源码行为扰动。
4. 编辑并重新构建 suba 内核及其必要 S0 汇编，直接生成完整、可启动的 ELF。
5. 将构建产物正常持久化；允许宿主按字节搬运该 ELF，经固定 RAM 启动链装载后观察新行为，并再次编译普通应用。

运行库适配、必要汇编处理和构建组织属于系统内构建闭环。首版不要求 guest 安装、切换或回退内核，不要求磁盘 stage0 的原生重建检查。宿主部署只允许读取和按字节搬运已保存的产物、校验身份及启动固定加载配置；不得重新编译、汇编、链接、重打包或修补 guest 的 ELF。guest 输出、搬运副本与实际装载文件必须全文件一致。这一边界称为“原生构建完成，部署仍依赖宿主”，不称全原生部署。

宿主工具可用于初始引导、制作初始磁盘、测试、观察，以及上述按字节搬运部署。初始可信种子、不可变启动基础、可在系统内重建的部分，以及每一步的输入与输出，必须在引导方案中明确列出。不能把已有 Linux-user 自举证据当作 suba 内自举证据。

编译器迁移时保留现有 Linux-user 回归路径。语言或编译器变更应由实际系统需求驱动；不以抽象的通用性为理由同时扩张语言和内核范围。

## 4. 多进程与故障边界

普通应用是需要隔离和管理的执行实体。它们的越界访问、崩溃、无响应或终止，应能被系统处理，而不破坏其他进程的地址空间或阻止其他进程继续获得执行机会。

系统必须有能力终止无响应应用。应用不能仅凭拒绝主动让出执行权就永久占据 CPU。

每个进程持有的资源必须有明确归属和结束路径，至少涵盖：

- 地址空间及内存分配；
- 打开的文件、其他服务句柄；
- 等待登记、尚未完成的请求；
- 窗口、显示缓冲及输入关联。

正常退出、异常退出、强制终止都应走可解释的回收规则。资源不足时必须报告受控失败；局部申请失败不能遗留无人负责的资源。正常申请资源或使用 CPU 会产生共享资源竞争，隔离验收关注的是防止越权破坏、永久垄断和退出后的泄漏。

内核和驱动属于可信部分，其自身错误可以导致系统 panic。当前不要求内核、驱动或系统服务具备崩溃后的透明重启与故障恢复能力。将某个组件放入内核或系统进程，是后续架构选择，不能由本条直接推导为既定部署方式。

## 5. 持久文件存储

源码、编译产物和用户文件应能保存在虚拟磁盘上，正常保存、关机和重启后仍可读取。

文件系统必须支撑编辑与构建过程中的名字查找、创建、读取、写入、删除及存储空间回收。具体目录结构、磁盘格式、缓存策略、刷新操作及程序发布规则由实现规格明确。

当前不要求突然断电时的事务恢复、日志恢复或掉电原子更新。正常保存和关机仍必须具有明确的写回完成语义，不能把尚未持久化的数据声称为已经保存。

宿主可提供块设备后备文件；文件组织、空间分配和回收由 suba 实现。

## 6. 桌面、编辑和文本

提供传统的可重叠窗口桌面，纳入系统整体设计。应能让多个程序拥有各自的交互区域，并具备明确的叠放关系、输入焦点、窗口操作和应用结束行为。

至少包含可用于系统内开发的文本编辑环境，以及编译结果、诊断和程序运行结果的展示方式。编译或某个应用等待时，桌面及其他可运行应用仍应能够响应。

明确窗口关闭与进程结束之间的关系。应用异常或被终止后，其窗口和输入资源应被回收，不能留下无法移除的界面或持有输入焦点。

文本需求：

- 正确读写 UTF-8 文件。
- 基本文本显示、光标移动、选择和编辑保持正确的字符边界，不能把一个 UTF-8 字符截断。
- 支持中文字形显示和基本中文文本编辑；支持字集及缺字行为必须公开。
- 不实现中文输入法和复杂字体排版。

具体字体来源、字形数据布局、字符覆盖、渲染与编辑粒度在实现规格中定义。字体数据及必要处理工具单独计账，不能把已有字体数据混同于自研排版机制。

## 7. 架构清晰与成本

没有特别的行数上限，也不继承 SOS 的旧预算。架构必须足够清晰明确。

每个核心模块的设计应回答：

1. 它解决什么问题，对外承诺哪些行为？
2. 哪些状态由它拥有，谁可以改变这些状态？
3. 请求可能在哪些地方完成、失败或等待，谁负责继续推进？
4. 资源何时创建、交接、失效和回收？
5. 它依赖哪些模块；哪些属于核心机制，哪些属于平台条件？
6. 如何单独测试，以及如何在完整系统中观察同一行为？

架构文档必须能解释至少三个跨模块过程：一次程序启动、一次需要等待的文件或输入请求、一次异常退出后的回收。接口形式应服务于这些过程，不先建立通用框架再寻找用途。

内核、汇编、驱动、文件系统、桌面、编辑器、用户库及系统内构建工具全部记录实际规模。已有编译器、测试、宿主辅助工具、外部基础设施及字体数据分别列账。移动目录、改成系统服务或引入生成工具不会自动消除成本。

## 8. 整体验收场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| 启动与交互 | 固定 QEMU 配置启动进入可使用的窗口桌面，键盘和鼠标交互有效 |
| 多程序 | 至少两个应用同时存在；窗口可重叠并正确获得输入，计算或等待不会冻结整个桌面 |
| 应用隔离 | 一个应用非法访问、崩溃或死循环后可被处理或终止，另一个应用的数据和继续运行能力得到保留 |
| 回收 | 反复启动、失败和终止应用后，进程拥有的内存、句柄、等待登记和窗口资源回到预期状态 |
| 文本 | 打开包含中文的 UTF-8 源码，正确显示并编辑，保存后字节内容符合预期 |
| 持久化 | 保存源码与构建产物，正常关机重启后重新读取并验证内容 |
| 应用构建 | 在系统内编辑源码、编译、查看诊断并运行产物 |
| 编译器自举 | 在系统内构建后续编译器，验证完整产物固定点，并通过源码扰动证明源码确实参与构建 |
| 内核原生构建 | 在系统内分别修改 VT 和必要 S0，生成并保存完整 kernel ELF；同输入与宿主构建全文件对照；宿主仅按字节搬运，经固定 RAM 启动链运行新行为，再完成应用编译；不声称 guest 自行部署 |

这些是完整交付的门槛，不要求所有能力在第一个实现阶段同时出现。阶段计划应保持同一条整体设计主线，并明确每个中间产物尚未满足哪些门槛。

## 9. 后续工程决策与验证

以下内容由现有架构与后续分阶段实现细化并验证，不构成继续向用户逐项询问实现细节的前置条件：

- 内核、系统服务、桌面和应用的职责及部署边界。
- 地址空间布局、保护、执行现场、抢占和等待表示。
- 服务调用、句柄、跨进程数据访问及资源配额规则。
- QEMU 设备组合、必要驱动、启动入口及陷入接口。
- 文件系统与启动产物格式、原生内核构建及宿主按字节搬运的身份验证；系统内选槽/更新另行延期。
- 窗口及输入协议、显示缓冲归属、编辑器和编译器协作方式。
- UTF-8 编辑细节、中文字体覆盖与必要数据工具。
- 编译器的平台依赖拆分、目标汇编支持、系统内构建入口。
- 内存和存储容量：须计入运行中的编译器、内核、显示缓冲、文件缓存和构建输出的实际需求。

进入实现前，应交付一份能贯通第 8 节场景的整体架构说明、关键接口和状态生命周期、依赖顺序及可执行验收计划。对平台、编译器移植和构建链的未知项可以先做有界验证，但不能把验证样本替代最终系统。
