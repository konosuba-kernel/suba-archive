# suba 实施依赖、探针与验收

2026-10-15，执行更新。**K0、K2a、K2b（实际 RAM 接管）已验收；按用户要求持续完成剩余 K2 至 K7，每个大环节验收后提交。** 磁盘部署 K1 延期，不再阻塞首版原生构建。范围依据见 [SCOPE_REVISION](SCOPE_REVISION.md)，当前执行记录见 [推进至 K7](../docs/workflows/through-k7/DELIVERY.md)。架构依 [ARCHITECTURE](ARCHITECTURE.md)，接口依 [CONTRACTS](CONTRACTS.md)。调查/本轮设计的已执行记录在 [DELIVERY](DELIVERY.md)。

## 1. 实施原则

先证明工具链、RAM 启动交接和运行期最容易失败的边界，再把同一组机制组合为可交互系统。每阶段交付真实路径与有限负例，不累计彼此不兼容的演示内核。首版整体目标不改成“先做 Linux 兼容层”或“先把解释器塞进旧 SOS”。

每个实现节点有独立 reviewer、冻结候选和证据目录，依赖的最新候选通过后才正式启动。执行前绑定真实 agent 身份；以下 owner 是待派发职责，不是已经工作的代理。共享 ABI/磁盘布局、kernel dispatch 和根构建清单由集成负责人独占写入，下游通过已冻结合同消费。复用同一 agent 可跨节点，但不得自审自己的产物。

K4 存储负责人是最小 virtio/block 传输及队列生命周期的唯一生产所有者，不依赖延期 K1。将来 K1 消费 K4 已验收的低层格式/传输源码，只增加引导期有界轮询与设备交接上层，不维护第二套驱动。共享字段由 ABI 所有者维护。K2 使用当前固定 RAM 引导进入真实 kernel；用户映像 fixture 仅用于局部隔离验证，正式应用装载在 K4/K7 接回同一 FS/ELF 路径，不保留第二套生产 loader。K6 的编辑算法/字体处理可在 Linux 用户侧运行，但其图形和保存验收必须到 K7 在 suba 完成。

K2 分段交付：本轮 K2a 仅实现可信 RAM/保留范围上的物理页分配、清零、身份校验与回收，并在 QEMU 真实读写中接入。它不包含 Sv39 页表、U-mode trap、抢占、进程表或隔离完成声明。K2b 已完成实际 RAM 与保留范围接管；剩余地址空间、trap、调度和进程生命周期合并为完整 K2 实施与验收，不再按内部强依赖拆细代理。通过 K2 表中全部验收后，才解除 K3 的依赖。

有限并行：K2/K6 可在 K0 后并行；K4/K5 可在完整 K3 后并行；K7 是强制汇合。延期 K1 不占首版关键路径，也不能以 K2a 局部通过代替完整 K2/K3。集成负责人在每次汇合核对合同，不把各组件“通过”直接等同完整系统通过。

## 3. 最先冻结和验证的事项

K0 已产生 `abi/contract` 的固定记录：BootInfo/TrapFrame/启动参数、syscall号与错误、句柄代数、窗口事件、磁盘头/FS字段偏移。用当前语言能读取的普通文本或VT常量表达，保留一个权威来源；如果使用生成器，生成器自身也用S-next并可系统内构建。不能仅在宿主Python中生成关键汇编偏移，形成新的隐蔽依赖。

K0已验收的S0 CSR/fence/sret/wfi、fw_cfg所需sh及对齐规则，继续保留机器码对照及非法操作数负例；GNU工具可作独立测试oracle，不能在正式产物流水线修补或重链接。若不用M-mode路径，则不因“完整ISA”增加mret/AMO体系。

K0 不重做语言设计。维持现有核心语义；运行环境模块与target布局是编译器边界。32源文件限制若妨碍合理模块拆分，依据实际清单统一提高至64并验完所有关联表/边界/内存；不为凑32把模块塞成巨型文件。其他容量先统计再改，不默认无限增大。

延期 K1 将来恢复时必须验证真实磁盘链；此前 RAM 标记复位探针不能证明磁盘持久化。首版 K4 仍必须验证普通文件 sync/FLUSH 及正常关机后的新启动读取。既有启动槽大小32MiB/位置和发布调用号保留，不重新划给 FS、不复用编号；kernel最大64MiB内存跨度与普通文件16MiB上限仍是独立校验。

K2/K3 最危险的是 trap 与内核推进上界：调度必须在每片后获得机会，所有copy/clear/scan/close/reap 都不得在关中断区遍历无限输入。初始每步数据量≤64KiB，表扫描≤64项；实测之后可调。目标是在指定QEMU环境、两个编译任务背景下，交互请求开始处理延迟99%≤100ms、单次S-mode连续工作≤5ms；这是**测量目标**而非实时保证，未达时先找无界循环和多余复制，不直接增大时间片掩盖。

K4 固定 virtio modern transport、一个split block queue、VERSION_1与FLUSH；不协商未实现feature。应用kill与DMA完成的先后顺序、空间预留失败和元数据IO错误是单独案例。设备故障停机与普通应用失败回收分开记录。

K5 冻结固定1024×768/30Hz上限，观测完整合成耗时和像素拷贝量。ramfb前缓冲3MiB在启动时预留连续物理页。全窗拷贝可分片，合成器用户态可被抢占；如果绘制落后，丢弃中间损伤并合并重绘，不能把渲染推入不可抢占内核大循环。

## 4. 跨模块验收矩阵

| 需求场景 | 正向场景 | 必要反例与证据 |
|---|---|---|
| 启动/设备 | 固定正式命令进入桌面，UART只作诊断 | 缺设备/错误feature/错误RAM/错固件受控停机；记录QEMU/固件/源码/产物身份 |
| 多进程隔离 | 两应用分别写私有内存并持续显示计数 | 写内核/其他进程、用户CSR、非法指令、除零panic、死循环；受害应用数据和计数仍正确 |
| 资源回收 | 正常退出/关闭与强杀同一基线 | 至少100轮分别kill装载中、就绪、流等待、磁盘等待、窗口更新后的进程；页/句柄/等待/表面/在途请求回基线，缓存warmup另计 |
| usercopy/身份 | 跨有效页读取/写入 | 地址加法溢出、跨guard、RO目的页、超长记录、错误对象类型、关闭后重用槽/迟到完成；kill无关进程/可信desktop、伪造Child、PID复用均拒绝；内核不panic |
| 桌面 | 两窗口重叠、焦点、拖动、CloseRequested | 不响应close的应用强杀；快速创建销毁/大量motion/键队列溢出；无焦点残留或stuck key |
| 中文文本 | UTF-8中英混排、选择/删除/保存再打开 | 4字节缺字原字节保留；组合字符按已声明粒度；非法UTF-8拒绝；文件超限不破坏旧文件 |
| 正常持久化 | 保存后sync、正常关机、重启比较全字节 | NoSpace/节点满/temp创建失败/未seal compiler输出；旧文件仍可读、空间无漏；关机时已有DMA/临时文件仍正常收尾；不把拔电测试列为本版门槛 |
| 构建闭环 | 编辑→诊断→改错→编译→运行，另窗响应 | 复制期间修改源得到Busy；冻结后写/replace/unlink及旧写句柄都拒绝，src/out权限分离；构建时继续编辑不改变本轮输入；流满/关闭/取消/父退出清理；失败构建不产生可误认成功的发布产物 |
| 编译器自举 | 原生C0→C1→C2→C3及可观察扰动 | 空宿主工具依赖；检查产物来自本次执行而非旧文件；保存全部清单/完整哈希/差异 |
| 内核原生构建 | guest分别修改VT及S0，完整ELF保存；host仅搬运后固定RAM链启动观察新行为，再编译应用 | 同输入host/guest全文件对照；坏ELF/超文件或地址窗口/源修改竞争/构建取消；拒绝旧产物、搬运损坏及host修改；记录guest输出/副本/装载身份；不要求guest选槽或stage0原生重建 |

每份记录需说明实际执行环境、输入版本、动作、期望、结果和原始日志路径。通过图形验收需要真实输入或QMP输入注入与guest事件、可见帧对应，不只调用绘图函数。存储验收用真正磁盘后备文件与新启动读取；host负责建初始盘、启动、注入测试输入和观察；K9另允许按字节搬运guest已保存的完整kernel ELF，不能代做构建或修补。正常文件持久化验收仍由guest新启动读取完成，host导出不能代替它。

测量资源回收时区分可复用缓存与泄漏：预热到稳定基线，记录每类对象活数、页owner、设备引用；等待有限的排空期限后比较。不能只看某个用户进程已从列表消失。坏设备永不完成的场景应得到已声明故障停机，不能计作“完整回收成功”。

## 5. 目录、读者路线与成果边界

计划目录（不是现有实现）：

```text
suba/
  abi/                 外部记录、偏移与版本的唯一来源
  boot/                固定RAM引导与suba-boot清单；磁盘stage0延期
  kernel/              machine、memory、space、process、request、fs、device、window
  user/libsuba/        系统调用包装、文件/进程/事件的具体结果类型
  user/text/ draw/     UTF-8、字体、裁剪和绘制
  user/desktop/ edit/  窗口策略与开发环境
  tools/               build、fontpack、镜像初始化/校验；目标工具与host脚本分开
  assets/              字体源、许可、固定资源
  tests/               单模块反例、QEMU端到端、故障/回收和自举记录
  docs/                面向使用者的版本参考、读者路径、实测成本
  design/              本架构与决策证据
```

不复制另一个compiler维护树到suba；源码仍由 `biomiya/compiler` 维护，初始磁盘和本机构建快照包含明确版本的源码副本。`SOS/` 不参与构建或需求。当前工作区根不是 Git 仓库，suba 与 biomiya 各自为独立 Git 仓库。编译器 tools/tests/bootstrap 已按职责迁移，见 [迁移说明](../../biomiya/docs/layout-migration.md)。每轮保持跨仓库变更清单、输入身份及各自产物版本，不能只提交 biomiya 便声称 suba 已被版本化；本轮按用户新授权，每个大环节验收通过后提交一次。

教学说明按三条路径组织：`spawn→ELF→页表→首次sret`、`read→Wait→IRQ→copyout→恢复`、`fault/kill→令牌失效→资源释放→退出记录`。最后接上`edit→compiler→持久保存→host按字节搬运→固定RAM链启动`，明确原生构建与宿主部署边界。每条路径给真实源码入口和状态变迁，避免按目录逐文件讲解却看不到系统行为。

规模与性能到K10给实测结果，当前不预测行数或交付天数。需要扩展语言、设备组合、地址模型或运行时并发方式时先返回对应合同说明影响，再修改依赖；不能默默把未验证的实现选择变成新需求。
