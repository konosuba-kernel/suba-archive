## 2. 必须修复的合同

### R1：快照没有对应的不可变名字空间和采集一致性规则

位置：`ARCHITECTURE.md:115`；`CONTRACTS.md:58`、`:118`、`:124`、`:144`–`:146`。

架构承诺“冻结所需源文件”“构建期间的变化进入下一次作业”，但 `/work` 包含快照且默认普通应用可写；`seal` 目前只承诺退出后保留文件。独占写只保护已经打开的同一节点，不能保护编译器尚未打开的文件路径，也不阻止原子 replace 换成新节点。

反例一：快照完成后，程序修改或 replace 快照中的第二个源文件；编译器先读取第一个，再打开第二个。它仍严格遵守逐文件读锁，却得到与构建记录不同的输入。反例二：复制源 A 后编辑器保存 A/B，再复制 B；得到跨保存时刻的组合。对象复用 generation 不能检测同一节点内容被修改。当前没有声明接受这种弱快照语义，也没有避免它的机制。

必要修复：

- 选择并写明采集语义。可以有限复制后验证内容/名字空间版本，变化就撤销并报 Busy，不要求通用原子 FS 快照。
- 冻结输入树必须由内核强制禁止内容写、名字替换/删除等操作；输出目录独立可写。明确准备者、seal 权、子编译器只读访问、旧句柄是否仍能写、取消后由谁清理。
- 编译器清单的相对路径/输出路径必须在这种布局下可表达。清单本身、S0、策略输入与诊断对应的源都属于同一冻结输入。
- 加入复制中修改、seal 后修改/replace、旧写句柄、取消/父退出清理的验收。

如果采用“保持所有源打开”替代冻结树，还必须处理 64 句柄上限与可能的 64 VT + 8 S0，以及名字路径指向新节点的问题；仅在文字中增加“只读”不能解决合同。

### R2：普通 kill 的授权范围必须明确

位置：`CONTRACTS.md:40`、`:52`–`:56`；`ARCHITECTURE.md:46`–`:48`。

文档定义了普通 Process.kill、Child 对象、rights 和 desktop 的强杀管理权，但没有规定普通 kill 要消费哪种句柄/权利或允许哪些对象。不同实现者既可以合理写成“父只能杀自己的 Child”，也可以写成“同用户可按 PID kill”；后者会让普通应用结束无关应用乃至可信 desktop。内存隔离和防注入特权本身并不能阻止这个反例。

必要修复：普通终止操作明确为自退出或持有带 Kill 权的 Child/Job 句柄，只涉及自己的子作业；裸 PID/窗口身份仅用于定位，不构成授权。全局终止须 desktop 的独立管理权，且说明可信系统进程是否可被其终止。collect_exit、子树取消同样限定于持有的 Child/Job。加入越权目标、伪造/过期句柄、PID 复用负例。

这是保护边界缺少确定语义，不是现有实现存在安全漏洞的断言；目前没有产品实现。

## 4. 重点反例分析

- **共享栈与等待：**请求保存 continuation 数据而不保存睡眠中的内核栈，单线程用户进程等待时不能同时 free 用户页，完成重新校验 token 和页权限。kill 先撤销再回收，能覆盖等待中退出；单核 S 中断关闭使这些短状态转换串行。长循环必须分片，真实延迟仍无法由设计证明，K2/K3 已设门槛。
- **DMA 晚于退出：**设备只持有内核 bounce 页，进程退出可释放用户页但必须等设备完成才能回收 bounce。无完成超时走可信平台故障停机。这与“普通应用完整回收”一致，未将坏设备纳入正常回收承诺。
- **窗口释放时桌面仍绘制：**桌面只持有已经拷到本地的像素；窗口代数变化使下次 copy 失败。容许最后一帧旧画面不等于读已释放表面。64 KiB 同步拷贝不跨调度保存窗口页引用，合同闭合。
- **文件 replace 与旧 reader：**名字关系切换，旧 reader 保持旧节点引用，最后引用释放才回收。打开 ELF 验证期间禁止就地写，足以避免发布/装载 TOCTOU；尚未打开的多文件快照不受该机制保护，故单列 R1。
- **取消发布：**选择头提交前可放弃；一旦进入 WriteBootHeader 就由内核完成正常写回。它不要求用户进程继续存活，不把 cancel 等同撤销磁盘写。掉电不承诺原子更新，边界明确。
- **固定启动基础：**stage0 不挂载 FS、不接管运行期 trap/驱动；kernel 必要汇编必须原生构建。stage0 原生一致性检查比用户最低要求更强，但不伪称 QEMU/OpenSBI 自举。
- **容量：**371 MiB 场景预算和 141 MiB 余量算术正确；16 个最大窗口为 48 MiB，ramfb 独立 3 MiB。FS 191 MiB 内 FAT/节点表有足够地址容量。编译器 RW 55,135,764 B 由 ELF 实读一致。完整系统是否满足 512 MiB、64 MiB ELF跨度、128 KiB kernel 栈及 2 MiB stage0 **无法判定**，文档正确将其置于实测门槛。
- **语言与模块：**有限枚举分派、数组/指针和显式 state machine 均可用现有 S-next 表达；MMIO 不假装 volatile 普通指针。平台运行环境/产物 profile 正交，固定桥绕过当前匿名符号障碍，无需任意函数指针。实际 import DAG 和各表余量须在 K0/各清单形成时验证，不能本轮凭规划计为已通过。
- **实施顺序：**K0→K1/K2/K6，K3 后并行存储/桌面，K7 汇合再 K8/K9，最后 K10；无环且无正式产品绕过工具链/保护/资源合同。K1 轮询与 K4 IRQ 共用传输底层的写入协调明确。

## 5. 非阻塞建议与无法判定项

1. `CONTRACTS.md:150` 的“禁新写”明确限定为拒绝新用户写请求；内部已接受事务、临时清理、发布头收尾和 sync_all 仍允许继续。现有 §3/5/7 已要求这些系统收尾，可作一致解释，因此本轮不单独列阻塞；应加入关机中已有 DMA/临时文件/提交头的组合验收。
2. `IMPLEMENTATION.md` 中 K2 的“32寄存器现场”可写为“x1–x31 加 trap CSR，x0恒为0”，与合同 280/288 B 避免表面歧义。
3. 普通文件 16 MiB 小于 32 MiB 启动槽是两个独立上限，本身不矛盾；实现参考应说明首版从普通文件发布的实际文件上限仍受 16 MiB 限制，避免把 32 MiB 槽误认为工具链可交付尺寸。
4. A/B 原始探针本轮未重跑；guest 块/input IRQ、1024×768 ramfb 初始化、GTK交互、磁盘发布后复位、延迟和内存峰值均**无法判定为实现通过**。它们作为 K1–K10 门槛是合理的。
5. K0 才冻结 ABI 调用号、字段编码和编译可用的常量清单是本次架构阶段允许的安排；不应提前随意填数字制造稳定 ABI。R1/R2 属于需要先决定的语义，而不是可以纯机械延后的偏移量。

本候选保持不通过，直到新冻结候选解决 R1/R2 并经独立复核。允许 A/B 调查事实沿用相同哈希；本报告不授权将未经复核的新 C 直接标成通过。
