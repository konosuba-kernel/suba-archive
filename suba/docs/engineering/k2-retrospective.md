# K2 实现记录回填

来源：提交 `72e19fb` 的 `docs/workflows/through-k7/K2-report-r1.md`、`K2-acceptance-r1.md/json`、`K2-independent-r1.py`、`K2-stack-r1.py`。以下不补造当时没有保存的诊断细节。

## K2-E01：测试探针自身破坏 x31

- 类别：测试实现问题；状态：已解决，K2-r1接受。
- 症状：全寄存器陷入/恢复探针失败。`build/k2-registers-1`保留早期失败。
- 已确认原因：S0的伪branch/jump使用x31作为临时寄存器；原自循环破坏了自己声称要验证的寄存器。
- 处理：使用真实jalr自循环，随后真实定时陷入验证x1..x31恢复。另有删除x28恢复指令的负控准确panic80。
- 改进参考：机器操作/伪指令手册应把隐式clobber醒目标明；寄存器验收夹具须单独核对最终指令。不能仅凭该失败归咎于trap实现。

## K2-E02：ELF零长度范围和异常分类的边界

- 类别：内核实现边界修正；状态：候选冻结前解决。
- 已记录修正：ELF total≤64MiB；零文件字节的BSS页不计算无用文件偏移，避免巨大p_offset参与溢出；未支持的高位中断在修改进程状态前拒绝，不能用128+cause把中断误作应用异常并溢出。
- 验证：37个decoder边界、真实RWX拒绝、未知中断注入panic10；另有用户写只读argv页的独立硬件反例。
- 改进参考：空操作应有明确语义，不执行无效地址运算；fault/interrupt分类应先于资源状态转移。保留分型返回与可信顶层panic，不为节省分支混用编码。

## K2-E03：单函数frame不是完整栈上界

- 类别：规模与可审计性难点；状态：K2测量完成，后续阶段仍需复核。
- 实测：最大frame9344B；独立直接调用图估计start链24944B、dispatch5584B、panic1024B，加小型汇编桥，未见递归。128KiB共享内核栈充足。这不证明未来K3–K7调用图仍满足相同界限。
- 元数据成本：页归属账本4.5MiB、allocator1.5MiB，不只计算逻辑代码行。K3动态free需要复用账本空洞，不能继续只追加并永久消耗额度。
- 改进参考：编译器应提供可追溯的frame/调用图成本报告；大值复制、固定表和资源生命周期同时审计，不能以源码短小替代内存成本分析。
