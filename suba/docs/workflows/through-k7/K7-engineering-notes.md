# K7 工程过程记录

K4/K5 完成前的隔离探索不构成正式验收。K5提交 `92c76d2` 后正式启动K7；root维护此总记录，内核作者另维护 `K7-kernel-notes.md`。早期草稿在 ignored `build/through-k7-k7-draft/`，必须经正式集成重新验证。编译器核心来自 biomiya `bd73055`，使用已接受 C64 E3；不得把 Linux 上生成 suba-user ELF 等同于已经在 suba 内编译。

## K7-E01：文件过长的错误语义仍隐含宿主数字

- 类别：架构接口缺口；状态：源码对照确认，原生系统路径尚待验证。
- 证据：`biomiya/compiler/runtime/host_linux.vt` 声明错误数字为宿主局部诊断；但 `compiler/input.vt::read` 特判 `CountResult::Failed(17)`，将其转换为 `I_LIMIT`，其余错误一律 `E_IO`。`runtime/linux.vt::read_buffer` 用17表示填满含一个探测字节的输入缓冲。
- 影响：直接在 suba adapter 返回 `abi::LIMIT`（9）虽然能拒绝过长输入，却会丢失编译器容量诊断。这里不是 suba 内核 BUG，也没有观察到越界写；问题是运行环境边界没有完整表达上层实际依赖的错误种类。
- 临时探索：adapter 明确保留17这一现有内部约定，避免误报“宿主无关已完成”。正式 K7 接入时应将缓冲过长写成具体结果或明确的跨宿主常量，并同步验证 Linux/suba 两个后端与消费端；无需引入通用错误框架。
- 改进参考：平台移植审查除了查系统调用号，还应查上层对下层错误码的分支。接口注释不能代替实际消费点核对。

## K7-E02：suba-user 测试清单遗漏退出桥

- 类别：测试夹具缺陷；状态：首次真实编译返回正确拒绝，修正后真实编译与逐字节核对通过。
- `native-compiler-r1` 中普通U控制程序成功启动suba-user编译器，编译器从真实FS读取清单/源码，经流写入诊断。清单只含VT入口，遗漏profile要求的 `__suba_exit` S0，因此guest与同输入Linux oracle均报 `E_LINK file=0 byte=0`，没有生成结果ELF；控制进程返回31，正常关机与物理页基线通过。这不是编译器移植失败。原始盘、compiler.log、boot.log保留。
- 修正：清单显式包含真实suba退出桥；同时纠正控制夹具在collect已消费Child后重复close的预期。第二项由K4作者先发现于cwd测试，提前修正本夹具，尚未在本夹具实际触发，不能称此处已复现。
- 改进参考：最小语言例子和最小可运行目标不是同一组输入；profile手册已明确桥合同，构建示例应包含必要运行支持。

- 修正证据：`native-compiler-r2` 在真实 suba FS 上编译，正常关机后只读提取 `/work/result.elf`，与相同输入的 Linux 编译结果完整逐字节相同（12289 字节，SHA256 `f35d9b9efac7ba4bc8110b766a10ba47b7463b3594b8239700016fb9bd56d059`）。编译器与控制程序均正常退出，物理页基线恢复；尚未通过 FS 启动生成程序，也未完成 K7 作业与界面集成。

## K7-E03：路径合法性不能只复用编译器的96字节检查

- 类别：跨层合同难点；状态：静态核对确认，仍属K7隔离草稿，未在生产闭环触发。
- 编译器 `runtime::bytes::path` 校验相对路径、空白、`.`/`..`和96字节总长；FS另外限制每组件63字节及树深度。快照还引入 `/jobs/<id>/src` 三层、保留文件名和 `src/` 前缀。单独通过编译器路径校验，并不能保证快照可以创建。
- 当前草稿 `manifest.vt` 已检查加前缀后的长度与重复完整路径，但还需检查组件长度、剩余深度、文件/目录前缀冲突（如同时列出`a`与`a/b.vt`），及输出与原清单/策略的冲突。正式接入前补成纯规划阶段的拒绝，不等复制到一半才发现结构矛盾。
- 改进参考：边界复用应复用一项已明确的证明，不将“路径合法”当作跨编译器、FS、作业命名空间通用的单一布尔事实；保留各层自己的有意义约束。

- 隔离修正证据：`build/through-k7-k7-draft/manifest-r2/verification.json` 的26项原生RV64测试通过，覆盖63/64字节组件、13/14级快照深度、92/93字节前缀预算、正反文件/目录冲突、保留名子路径、64/65源文件、中文路径及输出覆盖输入。另`context-verification.json`的9项测试覆盖清单外路径/策略和输出冲突；新增context接口仍待正式build消费者接入；不将此纯规划测试计为K7验收。

## K7-E04：先 seal 再 replace 留出未发布临时文件的退出窗口

- 类别：跨操作生命周期缺口；状态：从 K4 接口和 K7 保存流程推演确认，尚未实施/运行反例。
- K4 `replace_nodes` 只接受 flags=0 的源。编辑器和构建发布若使用 create(Transient) → write → sync(SEAL) → close → replace，进程在 seal 与 replace 之间被杀时，临时名字已脱离退出清理，却还没有成为目标产物。源目录属于 `/work`，Job 树回收也不会删除它。
- 拟在 K7 收紧实际发布合同：REPLACE 允许调用者自己的、已关闭写句柄的 Transient 源，在同一 namespace 提交中改名并撤销临时身份；其他进程的临时源继续拒绝。写入先 sync(false)，替换后显式 sync_all；提交前死亡清理临时源，提交后死亡保留已发布文件。编译器本身在 Job/out 中仍正常 seal，不能把两种所有权场景混成一个标志。
- 不承诺已提交名字修改可被取消撤回，也不引入突然掉电事务恢复。需要验证旧目标读者、未提交死亡、成功发布后退出及外部临时文件越权；实现与证据完成前保持待验证状态。
- 改进参考：单个 syscall 的回收正确，不代表用户把多个 syscall 串起来仍有完整发布边界。审查应沿真实使用路径寻找“最后一次仍受清理保护”的时刻。

K7-E01 正式修正开始：compiler host 的整文件读取返回 `ReadResult::Value/TooLarge/Failed`；Linux 私有17只在 `host_linux` 中转换，`input` 和 Blocking 策略读取消费具名结果。新增 `biomiya/compiler/runtime/host_suba.vt` 使用同一合同，不复制编译器核心。当前正在编译真实suba-user compiler和输入回归，尚未算原生集成通过。

## K7-E05：普通类型名 Result 被旧语法拒绝逻辑截获

- 类别：语言实现/参考一致性缺口；状态：真实编译复现，K7消费者改用具体名字，编译器修复留待语言轮次。
- `build/k7-build-worker-r1` 拒绝 `compiler_streams` 内普通 `struct Result` 的返回类型，报 `I_UNSUPPORTED file=19 byte=2139`。不是泛型或Result特例；声明和使用的是普通具名结构。
- 对照 `biomiya/compiler/parse.vt::type_inner/named_expression`：遗留旧语言拒绝分支把裸标识符 `Option`、`Result` 一律拒绝，参考的保留名字说明并未列出二者。改名为表达实际用途的 `Completion`，不扩大K7范围修改语言规则。
- 改进参考：移除旧特性时，应按实际语法形状拒绝（如类型实参），而非继续占用普通名字；回归需要覆盖“同名普通用户类型”，不能只测试旧泛型语法被拒绝。

## K7-E08：编辑器整帧上传放大合成工作

- 实测：旧组合GTK tiny程序一次Ctrl+B到完成约152.1秒；后台另窗聚焦等待15.07秒、保存显示
  等待14.53秒。宿主同时有构建/测试负载，不能将其解释为孤立性能基准，也不能宣称满足100ms。
- 结构发现：每次按键、诊断或状态变化都上传640×480整帧，30个窗口写请求分别通知桌面；
  合成器会在上传途中开始多次绘制，较小变化引起大面积复制。此项不等于已证明全部时间来源。
- 修正：用户态缓存上次成功上传的像素，逐行精确比较，只提交实际改变的连续行；缓存只用于
  显示，不作为文档状态。完整布局仍可读，首次画面仍全量，无哈希碰撞或修改内核复制上限。
  新实现须重新编译和跑真实GTK，同样保留旧慢结果，不能用改善猜测代替测量。

## K7-E09：磁盘观察器必须遵守可见目录项语义

- GTK修复源码后的画面为Saved/return42，初版只读观察器却报磁盘returnx2。复查发现它将
  `DETACHED`旧节点也加入路径表，重名时覆盖了新的可见节点，导致错误报告“保存未持久化”。
- 同盘节点9 flags=0为新文件，节点10 flags=2为已脱离名字的旧文件。修正观察器从冻结的
  `kernel/fs/codec.vt`读取DETACHED常量并排除不可见项；不改磁盘、不修改guest保存流程。
  正常重启读取仍须单独验证，不能仅靠修正后的观察器自证。

## K7-E10：大型静态存储的真实装载成本

首轮ELF内存跨度：compiler约56.19MB、build约21.38MB、editor约13.31MB；ELF文件分别仅
1.06MB/274KB/393KB。BSS不是“免费内存”：当前加载器实际分配和清零每页，spawn在映像准备后
才返回。后续优化可测分页装载、按实际容量组织arena及异步启动界面，不以隐藏BSS或偷偷缩容
声称项目更小。本轮不扩展为虚拟内存新机制。

## K7-E11：字节数组强转像素没有自然对齐保证

独立预审 `/root/k4_review` 发现编辑器 PIXELS 用u8数组保存，却以u32/usize绘制。
`k7-editor-r3` 实际推算PIXELS地址为0xa7f032，mod4=2；此前GUI运行成功依赖QEMU处理未对齐
访问，不能证明语言unsafe前提成立。此问题可能增加复制成本，但未将其确认为全部慢帧原因。

修正：PIXELS和desktop BACK均使用u32数组保证对齐；窗口上传显式借用字节视图，偏移按字节
计算，缓存比较/记账直接操作u32元素。保留旧编译/截图证据，修后组合须重新构建、GTK验证。
这也是今后语言/规约检查的具体用例：原始存储对齐必须由声明保证，不能靠本次BSS排列猜测。

## K7-E12：测试记录混淆种子与客体编译器身份

独立验收发现pipeline报告初始化`compiler_sha256`为宿主C64种子，后续记录guest产物时使用
相同字段覆盖。实际编译命令与system快照均保存了两者来源，未改变执行输入，但字段孤立读取
会误判换了种子。当前报告明确：种子22d2c8…、guest编译器872580…；独立验收核对二者实物。
冻结工具暂不修改，后续工具接口应分为seed_compiler和guest_compiler，避免同名字符串拼接
把不同阶段的身份合为一项。此项是证据表示错误，不是guest编译器结果差异。

## K7-E13：完整编辑构建后重挂载失败

最终GTK `build/k7-desktop-r1` 已完成真实编辑41→42、构建运行、另窗保存、错误/诊断/取消及
final-sync；停止后的源码/notes/ELF均与期望一致，无可见Job/临时文件。然而相同磁盘重启时
`reboot/serial.log` 报panic70，未进入桌面。不能将局部字节正确当作整个文件系统可重挂载。
原始first/reboot磁盘与失败记录保留，K7-r1退回返工，尚不提交。表层GTK错误是窗口未达到尺寸，
根本阻塞是guest挂载失败；观测工具已改为启动失败时优先报告serial panic，不扩大超时或改变预期。

E12工具字段也随本次必须返工分成seed_compiler_sha256与guest_compiler_sha256；旧报告不重写。

E13根因已由实施者和独立审查分别定位：同盘SHA256为
`17a23ce4a3ae8996a9f90c9abd6a31b9d151f782af9c8dc7e52f14e680df82a9`，node10为旧hello.vt，
flags=DETACHED、size73、block1148；生产纯校验器返回Fault(kind=4,index=10)。挂载无条件拒绝
非零flags，与sync可持久化旧读者版本的语义冲突。并未证明该盘存在FAT损坏。

r2修复先完整验证所有分配，再分片回收跨启动已无所有者的Transient/Detached文件，复用同步写回
并FLUSH后进入Ready；同时目录删除若仍有Detached子项返回Busy，避免父链失效。不会跳过临时
文件的坏链，也不承诺事务恢复。分片释放期间插入Sync的潜在风险经控制流核对不可达：有效
CLEAN_NODE使cleanup_step连续优先推进，结束前不选择用户请求；另需实际大文件回归佐证。

## K7-E14：回收专项的后续启动偶发panic70

r2原失败盘已两次启动通过；新专项`k7-kernel-remount-r1`第一次和reboot1通过，reboot2出现
panic70。与E13不同，这次磁盘纯校验器返回Valid，boot serial已写3。相同kernel/boot/U及完全
相同输入盘三次重放均通过。失败不能因此删除，也不能称已修复或简单归为测试错误。

独立审查注意到失败启动3.73秒、成功约2.69–2.73秒，与1秒设备watchdog相容，但目前仅为假设。
正在用只在错误分支输出的诊断副本区分hub、FS进度、timer及设备完成状态；生产源码暂未据此改动。

E14追加结果：失败分支诊断快照12次同输入启动均通过；受控I/O竞争两组各3次（直接复制后启动、
复制后仅对该文件fsync再启动）也全部通过。后台单次fsync最长1.36秒，确认施加了实际负载；
直接组启动3.07–4.26秒，预fsync组2.63–3.09秒，预fsync本身0.35–1.08秒。未捕获任何错误分支，
因此这些数据不能确认原panic是设备deadline、IRQ错误或测试误差。未改生产watchdog或放宽预期。

K7-r2完整GTK闭环、同盘重启、原盘修复和坏盘反例均已通过，但独立整体验收仍无法判定。该未归类
反例直接涉及K4正常重启这一前置合同，不能推给K10性能目标。原盘/所有失败、生产候选、失败分支
诊断快照及受控I/O时间记录均保留；当前不提交K7。后续需要捕获hub/fs/timer与block具体失败分支，
或找到可对应验证的状态机缺陷；继续增加无故障循环不构成该问题已经解决的证据。
