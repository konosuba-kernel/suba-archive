# K0：从编译器到S-mode内核入口

这一阶段实现固定目标与启动桥、必要S0机器操作、编译器运行环境边界，以及suba下的最小内核入口。精确完成状态、测试身份与独立判定见[实施记录](workflows/k0/DELIVERY.md)。不把该阶段当作完整内核或系统内自举。

读代码先看[内核入口](../kernel/entry.vt)：验证K0允许的BootInfo范围和必要字段，建立早期异常入口，输出交接成功后停机。然后看[机器边界](../kernel/machine.vt)与[S0实现](../kernel/machine.s0)：UART有界轮询、CSR、fence、无栈紧急诊断及wfi停机。普通panic报告reason；可信异常报告scause/sepc/stval，不尝试恢复错误内核。

[编译清单](../kernel/kernel.build)直接交给S-next，profile为suba-kernel。编译器生成入口栈/BSS初始化，最终ELF不需要GNU assembler/linker修补。共享序列化格式来自[ABI常量](../abi/contract.vt)和[布局说明](../abi/README.md)，不依赖宿主生成关键偏移。

从suba目录构建内核（output必须不存在）：

```sh
mkdir -p build
qemu-riscv64 -s 1048576 ../biomiya/build/layout-p4-r1/e3.elf build kernel/kernel.build
```

内核入口接收BootInfo而非OpenSBI的hart/DTB寄存器；不能把这个kernel直接当正式`-kernel`启动件。当前[集成检查](../tools/check_kernel_entry.py)单独编译[boot fixture](../tests/k0/boot.vt)，QEMU预加载kernel ELF；fixture复制DTB、序列化BootInfo，然后真实跳入独立kernel入口。这个有限RAM交接检查没有磁盘读取、槽选择、CRC验证或重启发布，不是K1 stage0。

复现检查使用新的记录目录：

```sh
python3 tools/check_abi.py --compiler ../biomiya/build/layout-p4-r1/e3.elf --out build/abi-new
python3 tools/check_kernel_observer.py --record build/observer-new.json
python3 tools/check_kernel_entry.py --compiler ../biomiya/build/layout-p4-r1/e3.elf --out build/entry-new
```

入口检查覆盖正常boot→kernel、坏magic拒绝、可信非法指令进入紧急路径。boot fixture还通过真实fw_cfg设备验证16位大端selector、QEMU签名及目录计数；机器封装拒绝未对齐地址和超出16位的值。该检查不包含DMA或framebuffer驱动。串口标记之后持续观察500ms，要求没有错误标记且VM仍存活，再由测试工具停止QEMU；这只是有限行为观测，不能独自证明CPU始终处于wfi或系统可长期稳定运行。观察器要求boot进入标记后只有一个符合场景的完整终态，拒绝混合、重复或顺序错误的输出。除延迟panic和立即退出反例，还编译一份打印成功后触发非法指令的内核，要求真实QEMU运行被判为失败。观察器继续收集完整的500ms窗口，避免在紧急输出的第一个字节就终止VM。

K0内核只接受fixture给出的一条stage0保留区，不声称完整BootInfo保留字节/CRC/FDT验证。K1将实现原始磁盘槽加载、完整装载校验和正常重启；K2才加入页表、完整TrapFrame、用户抢占/回收与guard。当前内核没有普通进程、文件服务或桌面；编译器没有在suba内运行。

编译器只保留一个维护实现。host_linux提供六项编译器宿主操作；运行目标选择独立的target布局。真实suba服务后端应在K3服务合同可执行时接入，不提供返回假成功的占位实现。当前32源/8汇编上限未扩大；每份清单和内存成本据实际产物记录。
