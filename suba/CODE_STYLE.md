# suba 代码与风格规约

版本 0.1，2026-10-14。适用于 suba 的手写 S-next、S0、构建工具、示例和测试，以及为 suba 修改的编译器代码。已有编译器只在实际修改的范围内逐步遵循，不开展无关的全库格式重写。

本规约配套[整体架构](design/ARCHITECTURE.md)和[生命周期合同](design/CONTRACTS.md)，不替代[S-next 语言参考](../biomiya/docs/reference/s-next-0.1.md)。架构决定系统承诺，规约决定如何把承诺写成可以阅读、检查和维护的代码。K0 已实现并验收的 profile/桥/S0 指令以当前参考和验收记录为准；尚未实现的语言或机器能力仍只能写成明确标记的设计，不能当作当前语言语法使用。

K0–K10的代码实施与审查均参照本文；修改规则需说明对已有代码及验收的影响。规约本身不新增语言特性、内核服务或实现阶段。

## 1. 规则的强度

**必须**表示正确性或共同接口要求，违反时不能按本规约验收。**默认**表示共同写法，有明确收益时可以例外。**审查信号**要求解释设计，并非机械拒绝或硬性行数上限。

例外在相关代码或变更说明中记录：偏离哪项默认、具体原因、影响范围、怎样验证。一般工程取舍由实施者和独立审查者处理，不逐项向用户申请。必须项若与实际需求冲突，应先修订对应合同，不能以“风格例外”绕过所有权、保护和资源回收。

目标是让读者直接回答：输入是什么、谁持有状态、何时等待、失败留下什么、资源最终归谁。减少代码行数不能牺牲这些信息；增加抽象也必须证明它使这些信息更清楚。

## 2. 文件、排版和命名

| 项目 | 默认写法 |
|---|---|
| 文本 | UTF-8，无BOM，LF，文件末尾换行；4空格缩进、不用Tab、无行末空格 |
| 布局 | `{` 与声明/控制语句同一行；声明之间一个空行；每行一个普通语句 |
| 行宽 | 尽量≤100列；长路径、不可拆字符串和表格不为凑列宽扭曲 |
| 文件/模块 | `snake_case.vt` / `snake_case.s0`；模块表达职责，如 `kernel::memory` |
| 类型/枚举标签 | `PascalCase`，如 `ProcessId`、`ReadResult::Failed` |
| 函数/变量/字段 | `snake_case`；动作名加对象，布尔名表达谓词，如 `is_ready` |
| 常量/静态存储 | `UPPER_SNAKE_CASE`；可变static仅在所有者模块私有 |
| 类型标注 | `name: Type`、`fn f(a: T) -> R`；运算符两边和逗号后有空格 |

模块头依次写职责注释（必要时）、`module`、显式 `import`，其后按相邻职责组织类型、常量/状态、入口及辅助函数。不要强制全部私有函数放到文件另一端，让一条短路径来回跳转。同一模块可分文件，但整个模块仍是一个可解释的所有者。

名称应包含有意义的量纲：`byte_offset`、`page_count`、`deadline_ticks`、`physical_address`。小循环可用 `i`；不要让跨十几行的 `a/b/n/p` 代替业务概念。`utils`、`common`、`manager` 不能成为无归属代码的收集处；共享代码按具体职责命名为 `utf8`、`elf`、`endian` 等。

源码标识符用ASCII。默认源码合同和安全注释用简明英文，面向读者文档用中文；准确、自然的中文源码注释也可接受。不要求双语重复，不以注释语言妨碍正确解释。

## 3. 模块是状态与不变量的边界

每个持有状态的模块必须在头部或相邻模块说明中交代：职责、独占状态、允许调用的执行上下文、是否可能等待、对外不变量。纯编解码模块只需说明输入/输出和前置条件，不复制一份空洞模板。

- 一个可变表只有一个所有者。其他模块不得取得可写全表切片或通过公开字段修改它。
- 默认私有声明/字段；`pub` 是需要维护的合同，使用者实际需要才公开。不要为了测试把内部状态全部暴露。
- 接口表达动作，例如 reserve、publish、cancel、complete；避免万能 `set_field`、raw数组索引和大段“先get、在外面改、再set”。
- 调用依赖朝叶层：顶层dispatch→资源所有者→编解码与校验。叶模块返回结果，不调用调度器、桌面或任意上层回调。
- 同一事实只存一份权威状态；缓存/计数必须注明更新点及如何重新核对，不能各模块各维护一个“当前进程”或“窗口是否已死”。

局部计算的数据通过参数传入。进程表、设备队列等长生命周期状态可以用私有静态存储；不为形式上的“纯函数”把整个系统塞进一个巨型 `Context`，也不把原本可显式传递的局部值藏进全局“当前对象”。

ID/token用具体类型区分**容易混淆的身份域**，如进程、窗口和请求；raw表示只在所有者或边界编解码中出现。构造必须验证槽、代数和权限。普通字节数、循环计数不必全部包装成名义类型；有风险的跨单位转换应集中且命名清楚。

## 4. 函数、分支与嵌套

一个函数应处在一个主要抽象层次：解释请求、推进状态或执行字节操作。不要同时解析用户记录、分配页、改文件表、操作设备和唤醒进程；顶层函数通过具体步骤把这些动作串起来。

默认先检查前置条件和错误，早返回，成功路径顺读。return/break 后不再用 else 包住剩余正文。基于具体枚举的状态用穷尽match；普通真假条件用if，不为追求统一把简单判断也编码成状态机。

**审查信号：**函数主体约超过60行、控制流超过3层嵌套、参数多到无法一眼解释、文件约超过500行。这里不计函数外壳、结构构造和纯词法unsafe块为控制流层级。检查是不是混合了职责、遗漏结果类型或缺少边界；长度本身不是错误。状态转移表、指令编码表和测试样例可能有合理例外。

提取辅助函数必须得到可命名的动作、不变量或复用点。不要为了降低嵌套把代码拆成 `part1/part2`、几十个只转发一次的包装，或将关键步骤隐藏到另一模块。优先修正流程，再决定拆分。

下面是当前语言可编译的写法，先拒绝越界再计算，不使用危险的 `offset + length > total`：

```vt
pub fn checked_range(offset: usize, length: usize, total: usize) -> RangeResult {
    if offset > total {
        return RangeResult::Outside;
    }
    if length > total - offset {
        return RangeResult::Outside;
    }
    return RangeResult::Value(make ByteRange { offset: offset, length: length });
}
```

完整定义和运行例子见 [ranges.vt](docs/examples/style/ranges.vt)。`ByteRange` 私有字段使后续 `end` 可以依赖构造时的证明。这里没有引入泛型Result、`?`、隐式return或不存在的语法糖。

## 5. 数据、状态与适量函数式组织

默认用let，确有状态变化才用var。函数签名/公开字段显式类型；局部推断只在类型一眼明确时使用，无上下文数字写 `_u32`/`_usize` 等后缀。S-next只有单向局部定型，不靠编译器猜算式含义。

以具体枚举表达互斥状态和各自载荷。不要用多个布尔量表示 `waiting/dead/published/cancelled` 的所有组合；也不要把每个不相关标志强塞进一个指数增长的状态枚举。格式位域留在设备/磁盘边界，在内部转成受验证的状态。

范围检查、路径解析、UTF-8边界、布局和协议解码默认写成无I/O、无隐藏可变状态的函数。状态转换返回具体结果或小型动作，资源所有者执行副作用。无需让每个函数都返回“新世界状态”，无需统一effect框架、闭包或函数指针。

必须留意值复制：结构/数组按值复制，切片/指针只复制描述符且不延长寿命。大型buffer、页表、编译器arena不应作为按值参数/返回结果反复搬运；改为有明确有效期和访问权的存储视图。小型请求元数据/快照可以按值传递。是否“大”由调用频率、生成代码和栈预算验证，不设任意全局字节禁令。

不使用结构布局投机转换外部字节。磁盘、ELF、virtio、系统调用记录按协议宽度/端序显式读写；布局常量来自唯一ABI定义并验证。源代码枚举标签顺序不能悄悄成为可持久化格式。

## 6. 错误、结果与panic

可预期失败返回具体结果枚举：输入错误、无权限、容量不足、BadHandle、WouldBlock等。不要在内部用负整数位模式、神秘数字或bool兼任“失败/完成/等待”；外部ABI所需数值集中编码/解码。错误分类按调用者能采取的动作区分，不为每条失败语句创建一个错误类型。

无业务载荷的局部谓词可以返回bool；只有成功/失败且调用者无需更多信息的检查不必强造结果枚举。不得把本来需要错误种类或完成字节数的接口压成bool。

边界验证一次并建立内部不变量；内部只在真正依赖该不变量处断言。不要每个helper重复完整边界校验，也不能因“上一层应该查过”就接受尚未经验证的raw输入。接口必须区分已验证身份和外部数字。

普通应用传来的错误数据必须变成请求失败或该应用终止，不能因内核checked算术/下标panic停止系统。panic用于可信组件的不变量损坏和架构明确规定的系统故障；缺内存、用户非法地址、磁盘满不是内部bug。实际设备I/O失效按存储故障合同停机，不扩展成未设计的恢复框架。

失败必须传播或明确处置；忽略返回值需写明原因及后果。诊断在拥有上下文的边界生成，叶层不同时打印和返回同一错误。不要全链路重复刷日志。保留operation、对象身份/代数、phase和实际错误；内核诊断不需要借用户态日志系统才能输出。

## 7. 资源与defer

每种资源在所有者处必须能找到：创建/预留、提交或转交、关闭/取消、最终回收。返回一个ID并不自动说明所有权转移，接口需注明返回的是拥有引用、借用身份还是只读快照。

获得多种资源的路径默认分为“验证与预留→准备→发布”。发布前失败撤回本次预留；发布后失败遵循对象生命周期，不把已生效动作假装没有发生。状态变化和对应引用/计数在同一个所有者动作中完成。

`defer cleanup(args);` 适合局部确定的清理，登记时保存实参，panic不展开。**不能**在登记 `defer release(id)` 后把资源转交给另一个所有者，却忘了离开作用域仍会release；也不能传一个按值布尔量，期待稍后修改它能取消已登记清理。遇到提交/转交时明确组织成功与失败路径，必要时使用语义明确的abort helper。

关闭/flush失败需要影响结果时显式调用并检查，不塞进返回unit的defer掩盖错误。普通应用退出的完整回收依赖内核账本，不依赖应用清理函数。取消用户交付与结束设备DMA是两个时点，代码和命名必须体现区别。

## 8. unsafe、指针与机器边界

unsafe应小到读者能在局部核对理由，但允许同一证明下的一组访问或循环放在一个块内；不强迫每一行单独unsafe，也不默认包住整个大函数。

每个非显然unsafe区域都要有就近 `SAFETY:` 注释，说明地址来源、存活期/权限、边界/对齐、并发或硬件条件中的相关项。写“这里安全”“已检查”不够；同一证明可引用一个确切的函数前置条件，不重复整页文字。

公共函数若无法自行建立指针/切片存储的有效期与访问条件，应声明unsafe并写调用者责任。`unsafe fn` 内部仍按语言要求显式unsafe。参数检查仅证明长度，不证明裸切片背后的存储仍然有效。

完整的边界解码示例见 [bytes.vt](docs/examples/style/bytes.vt)：调用者保证普通RAM存活，函数自身检查4字节范围，再显式小端解码。这个函数**不是**usercopy；用户地址必须先作为整数UserRange经内核页表/权限检查，不能构造切片后交给它就视为安全。

必须区分普通RAM、用户VA、物理地址与MMIO。普通load/store不能冒充volatile或内存屏障；MMIO宽度、端序和fence由有限机器包装承担。DMA仅使用内核拥有且在设备完成前不会释放的页。不得保留指向调用者栈的跨等待指针；请求保留身份/代数/偏移等可重新验证的数据。

ABI边界的截位、回绕和移位必须注明意图。常规计数用checked算术；位协议确实需要模运算才用 `+%`、`-%`、`*%`，例如 `a -% b`，不能用回绕掩盖越界。缩窄 `as` 前检查可表示范围，除非明确执行协议的低位提取。移位先验证移位量小于位宽；当前无有符号整数，设备有符号数据在边界转换为明确的方向/幅度。

## 9. 等待、进度与执行上下文

可能等待的操作必须在接口中说明，并返回/保存明确阶段。不要用一个普通helper偷偷调度、轮询设备、递归重试或推进其他模块的全局事件循环。请求状态应让完成、超时、取消和迟到事件的胜负规则可见。

内核每个step必须有工作上界：字节、表项或明确有限的阶段数；单纯写 `while` 不等于有界。循环旁能够找到上界、游标变化和下一次推进者。大复制/清零/扫描/回收分片；工作片结束可返回More，等设备返回Wait，不能混淆为“尚未完成”。

默认避免内核递归；树/链遍历用有界游标或显式栈。使用递归需有深度上限及整条调用链栈预算，不能只凭单函数frame小就接受。单核仍有中断、等待、DMA和对象复用竞争，状态必须按合同串行化。

中断入口只保存现场、确认来源和登记有限事实；不格式化长文本、不解析文件、不分配大对象、不等待。引导期轮询是已有架构例外，必须有超时并与运行期路径明确区分。Blocking分析不证明IRQ安全、终止性或延迟；真实最长内核工作片须测量。

## 10. S0与平台代码

S0只处理启动、trap、SBI、MMIO/fence等机器边界。每个入口写清：profile/执行特权级、输入/输出寄存器、破坏/保留寄存器、sp对齐、x27处理及可能的异常/终止。

使用当前S0支持的数字寄存器拼法，如x10；注释可标a0。GNU汇编别名、宏、section、include等不得混入正式S0。CSR/sh等已通过K0扩展与独立编码/操作数验证；后续新增机器操作仍须完成同样验证，不靠宿主汇编修补正式镜像。

trap偏移、CSR/设备常量、页权限等有唯一权威定义。只在编码器或协议定义处集中出现必要数值，使用点引用具名常量；受当前整数match不支持命名const模式的限制，必要的数字分支就近注明协议含义，不能为消除数字制造不透明分派。

平台地址来自验证后的固定平台描述，不能散落在FS、窗口或编辑器中。无端口支持的机器行为必须明确拒绝，不能返回假成功让上层误以为功能存在。

## 11. 注释、文档和审查

注释解释理由、单位、不变量、硬件规则及非显然取舍，不复述语句。每个公开操作中不显然的等待、所有权、失败后状态应写在声明附近。大的算法附简短过程说明和边界，不用长篇行内散文掩盖结构问题。

TODO须说明具体缺口和可定位的计划节点/条件；禁止用TODO占位实现后照常返回成功。调试打印、临时绕过保护、静默放大容量和宿主依赖不能混进正式交付。

测试验证合同：成功与拒绝边界、部分失败回滚、失效身份、迟到完成、实际设备互操作以及整条自举路径。不要只比较两份使用同一算法的结果，或机械地为每个helper写镜像测试。纯格式/注释变更不要求重跑全部系统测试；影响ABI、所有权或目标编码时扩大到实际消费者。

规约示例在 [示例目录](docs/examples/style/README.md) 用冻结编译器编译并执行；它们演示当前语法和局部边界，不证明内核机制已经实现。未来formatter/linter先覆盖可靠规则，不用正则嵌套计数决定架构质量，也不为规约先写一套复杂检查框架。

每次代码审查至少回答以下问题，详细程度随改动规模调整：

1. 接口是否表达真实动作、错误、等待和所有权？公开状态是否扩大？
2. 成功路径能否顺读？嵌套/拆分是否由职责决定？
3. 不可信输入能否触发kernel panic、溢出、越权或无界工作？
4. 每个失败/取消路径的资源归属是否完整，迟到完成会不会二次交付/释放？
5. unsafe与汇编前置条件是否真实，是否引入隐藏全局状态、复制或宿主依赖？
6. 测试是否能区分关键反例，成本是否按实际代码和资源计入？

以上问题用于发现具体问题，不要求每次提交附一套空泛声明。审查应指出代码位置、反例和影响；不能仅凭“更优雅”要求改写，也不能用行数/覆盖率单个数字代替判断。
